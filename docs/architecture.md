# Архитектурные решения

## Границы компонентов

- React + TypeScript отвечает за интерфейс и вызывает REST API Laravel.
- Laravel реализует бизнес-правила и является единственным приложением, работающим с данными напрямую.
- PostgreSQL хранит сделки, принятые webhook-события и операции синхронизации.
- Redis служит транспортом для фоновых задач. Событие webhook сначала надёжно сохраняется в PostgreSQL; задача в Redis должна ссылаться на сохранённую запись, чтобы обработку можно было восстановить после сбоя постановки в очередь.
- В локальной разработке Vite проксирует API-запросы в Laravel; отдельная CORS-конфигурация не требуется.

## Версии внешней CRM и конфликт данных

`external_version` — последняя применённая версия источника. Время создания события (`event_time`) не участвует в разрешении конфликтов и не заменяет версию.

- Входящая внешняя версия больше сохранённой: внешние `title`, `status`, `amount`, `external_updated_at` и `external_version` применяются.
- Входящая версия меньше сохранённой: данные игнорируются как устаревшие.
- Версия совпадает, данные совпадают: событие считается повторным и не меняет сделку.
- Версия совпадает, но бизнес-данные отличаются: локальные значения сохраняются; расхождение фиксируется как конфликт для диагностики.
- Ручная правка не увеличивает `external_version` и сохраняется до появления более новой версии внешнего источника. Локальные изменения не отправляются обратно во внешнюю CRM в рамках тестового задания.

Проверку версии необходимо выполнять относительно актуальной записи внутри транзакции, чтобы одновременно выполняющиеся задачи не могли откатить сделку.

## Идемпотентность webhook

`event_id` уникален в PostgreSQL. Повторная доставка того же события, в том числе параллельная, не должна повторно применять бизнес-изменение. HTTP-приём подтверждается только после надёжного сохранения записи события. Redis не является единственным хранилищем принятой работы.

## Состояния фоновой обработки

Для входящего события планируются состояния `received`, `processing`, `applied`, `ignored` и `failed`. Для ручного запуска синхронизации — `queued`, `running`, `succeeded` и `failed`, с номером попытки и диагностической ошибкой без секретов.

Для временных ответов внешнего API используется ограниченное число повторов с возрастающей задержкой. После исчерпания повторов операция переходит в конечное состояние ошибки.

Webhook и синхронизация используют общий сервис применения внешнего состояния. Команда `operations:requeue-pending` повторно ставит в очередь durable-записи в `received`/`queued` и записи `processing`/`running`, зависшие дольше заданного времени. Повторная постановка безопасна: обработчик проверяет терминальное состояние и блокирует запись перед переходом.

Для синхронизации максимум три попытки; задержки между повторными запросами — 1 и 2 секунды. `429` и `5xx` повторяются. Другие неуспешные HTTP-ответы, например `404`, переводят операцию в конечную ошибку без повтора.

Таблица `mock_deals` хранит независимые данные внешнего источника. Режим `rate_limit` использует cache-счётчик: первые два запроса получают `429`, последующие — данные с кодом `200`. Режим `server_error` всегда возвращает `500`.

Счётчик `rate_limit` сбрасывается автоматически, когда синхронизация в этом режиме достигает конечного статуса `succeeded` или `failed`. Это позволяет повторять последовательность `429, 429, 200` без ручных команд и при этом не сбрасывать счётчик между повторными попытками. Ручной `POST /mock-api/deals/{id}/reset` остаётся для прямых запросов к mock API.

## HTTP API

- `/api/deals` — список с `q`, `status`, `page` и `per_page`; создание, просмотр и ручное редактирование.
- `/api/deals/{id}/refresh` — создание синхронизации и получение её текущего состояния в ответе/карточке сделки.
- `/api/webhooks/deals` — проверка секрета, валидация и надёжная регистрация webhook.
- `/mock-api/deals/{id}` — чтение или редактирование демонстрационного снимка; `?mode=success|rate_limit|server_error` выбирает сценарий чтения.

API mock зарегистрирован в stateless API middleware-группе без `/api`-префикса и CSRF-проверки браузерной web-группы.

## Индексы PostgreSQL

- Уникальный индекс на `webhook_events.event_id` обеспечивает идемпотентность.
- Уникальный индекс на `deals.external_id` предотвращает создание нескольких локальных сделок для одной внешней сделки.
- Индекс по `deals.status` поддерживает фильтр списка.
- Индексы по статусу и времени создания фоновых записей помогают находить ожидающие/застрявшие операции для отображения и восстановления.

## Допущения

- Внешняя CRM не получает локальные изменения.
- При расхождении данных на одинаковой внешней версии локальные значения сохраняются, а конфликт становится видимым в журнале обработки.
- Docker Compose и значения из `.env.example` предназначены только для локальной разработки; пароли и webhook-секреты для реальной среды задаются отдельно.
